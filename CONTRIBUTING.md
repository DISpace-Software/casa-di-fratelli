# Работа над SeatMap

Существующие правила архитектуры, именования, комментариев и проверок сохранены в [стандарте кода](docs/coding-guidelines.md).

## Первый запуск

1. Клонируйте `https://github.com/DISpace-Software/seatmap.git` и перейдите в папку репозитория.
2. Установите Git, Python 3 и инструменты своего приложения: Node 22 для веба, .NET 8 для API, Flutter согласно `mobile/README.md` для мобильного клиента.
3. Откройте нужный файл в `workspaces/` через VS Code / Cursor. Рабочее пространство ограничивает видимые папки, но не права доступа к репозиторию.
4. Для веба выполните из корня `npm --prefix frontend ci`, затем задачу редактора «Запустить локально» либо запустите `python3 tools/dev-hub/server.py` и откройте http://127.0.0.1:4310.

Задачи веб-пространств направляют запросы на локальный API `http://localhost:5183`. Для работы с данными нужен отдельно настроенный локальный сервер и локальные базы. Голые npm-команды могут использовать production-настройки; для первого запуска используйте задачи редактора. Настройку локальных баз согласуйте с владельцем API, а не копируйте production-подключения.

## Изменение → GitHub → публикация

```sh
git switch main
git pull --ff-only
git switch -c feat/cofein-menu-layout
# Внесите изменения, выполните проверки из инструкции приложения.
git add <изменённые-файлы>
git commit -m "Improve Cofein menu layout"
git push -u origin HEAD
```

Откройте Pull Request в `main` и заполните шаблон. Для слияния нужны успешные `web` и `backend`, актуальная ветка, разрешённые обсуждения и одобрение `Stepan2215`. Новые изменения сбрасывают старое одобрение. Для `Stepan2215` настроено персональное исключение из требования PR/review: чужое одобрение ему не нужно. Проверки сборки и ограничения force-push остаются. Для остальных действует обычный PR-процесс.

Владельцы указаны в [.github/CODEOWNERS](.github/CODEOWNERS). Единственный обязательный владелец кода — `Stepan2215`; другие сотрудники могут оставлять дополнительные ревью. GitHub использует CODEOWNERS из целевой ветки, поэтому новые правила владельцев начинают действовать после слияния этого файла в `main`.

После merge веб-проекты собираются в Vercel, production-публикация ждёт проверок. Сейчас изменение одного приложения может вызвать сборки других веб-проектов. Render реагирует на изменения backend, кроме Markdown. Мобильное приложение не устанавливается на телефоны от одного merge. Конкретные действия, миграции и откат: [регламент релизов](docs/release-operations.md).

## Доступы

Репозиторий публичный: для чтения доступ не нужен, для push нужен write-доступ или PR из fork. Доступ GitHub не предоставляет доступ к Vercel, Render, почте, базам или ресторанной админке. Выдавайте доступ только к нужным сервисам; повседневное изменение интерфейса не требует production-секретов. Control содержит ссылки, но не выдаёт права и не запускает деплой.

В тестах используйте локальные/изолированные данные. Не создавайте реальные бронирования и не рассылайте письма гостям для проверки интерфейса.
