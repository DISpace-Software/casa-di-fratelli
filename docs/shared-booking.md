# Общий сервис бронирования SeatMap

Создание и подтверждение по email выполняются в
`Services/Reservations/ReservationBookingService.cs`. Сервис не зависит от MVC,
контроллеров или `HttpContext` и использует уже выбранный ресторанный `AppDbContext`.

## Доступные маршруты

| Сценарий | Действующий сайт | SeatMap v1 |
| --- | --- | --- |
| Создать бронь | `POST /api/reservations` | `POST /api/v1/restaurants/{restaurantId}/reservations` |
| Подтвердить по email | `GET /api/reservations/confirm?token=…` | `GET /api/v1/restaurants/{restaurantId}/reservations/confirm?token=…` |

Оба HTTP-адаптера вызывают один сервис и используют общий перевод результата в
HTTP-ответ. Действующие тела ответов и статусы сохранены, включая текстовые ошибки
валидации, 409 при конфликте и 429 при превышении дневного лимита. Унификация всех
ошибок API в единый JSON-формат — отдельное изменение контракта.

Публичный v1 принимает имя, телефон, email, дату, время, гостей, выбранные столы,
зону, примечание, дату рождения и согласия — те же публичные данные, что сайт.
Это анонимный сценарий бронирования; глобальный аккаунт гостя пока не используется.
Чтобы приложение запрашивало только дату/время/гостей, ещё нужно реализовать
проверенную identity, заполнение контактов из профиля и серверный подбор стола
либо отдельный выбор стола/зоны в интерфейсе.

Поля `CreatedByAdmin` и `InternalNote` отсутствуют в публичном v1 DTO. Лишние
административные поля JSON игнорируются, не меняют правила и не попадают в бронь.
В старом маршруте эти поля сохранены для админки: `CreatedByAdmin=true` требует
проверки admin session, а ID/имя сотрудника передаются сервису из проверенного
principal. Сам флаг запроса не даёт административных прав.

## Ответственность сервиса

- Публичные и административные ограничения, часовой пояс, lead time и окно брони.
- Закрытие ресторана, сезонные зоны, столы для внутреннего использования.
- Нормализация контактов и ID столов, вместимость, дневной лимит контакта.
- Проверка конфликтов через действующий `ReservationConflictService`.
- Существующие правила первого/повторного гостя и email-подтверждения.
- Запись брони, столов, ресторанного профиля CRM и флага blacklist.
- Вызов уведомлений после успешной записи.

Правила времени вынесены в `ReservationTimeRules`; их также используют оставшиеся
методы изменения брони. Сервис получает `TimeProvider`, поэтому проверки границ
времени и срока токена не зависят от даты запуска теста.

Создание выполняет один `SaveChangesAsync`: бронь, связи столов и изменения CRM
сохраняются в одной EF-транзакции. Внешние письма/push в неё не входят.
Это атомарность записи изменений, а не блокировка одновременных бронирований.

## Уведомления

`IReservationBookingNotifications` отделяет доставку от workflow.
`ReservationBookingNotifications` использует действующие tenant branding,
отправителей EmailService, ссылку сайта ресторана и PushNotificationService.

Отправка выполняется с `await` после сохранения. Контекст запроса остаётся жив,
пока шаблон/branding используются отправителем. Для первого гостя это добавляет
к задержке ответа время попытки отправки письма; production EmailService использует
HTTP-клиент с таймаутом 5 секунд.

Исключение доставки логируется, а сохранённая бронь остаётся успешной. EmailService
также логирует собственные ошибки провайдера. Это предотвращает ошибочный 500
после сохранения, но не гарантирует доставку: постоянная очередь, повторы и
восстановление после падения процесса здесь ещё не реализованы. Для этого нужен
ресторанный outbox; он же должен питать будущую проекцию «Мои брони».

## Границы этого этапа

- Не изменены схема ресторанной базы и действующие правила статусов.
- Walk-in, ручное approve, перенос, блокировки, отмена, release и восстановление
  пока остаются в своих контроллерах. Все операции, занимающие/освобождающие стол,
  нужно включить в следующий этап координации записи.
- `FindTableConflictAsync` выполняет проверку перед записью. Пока нет общей
  транзакционной защиты всех путей записи от конкурирующих запросов, нельзя
  гарантировать отсутствие двойной брони при одновременных обращениях.
- Не реализованы idempotency ключи создания, вход гостя, привязка к глобальному
  профилю и outbox. Нельзя выдавать передачу чужого UUID за подтверждённую identity.
- Сохранены существующие fallback вместимости и фиксированные зоны Casa.
  Универсальная модель схемы посадки остаётся следующим отдельным изменением.

## Проверка

```sh
dotnet run --project backend/CasaDiFratelli.ReservationChecks
```

`BookingServiceChecks.cs` использует изолированные SQLite-базы, фиксированное
время, локальные перехватчики уведомлений и настоящий HTTP-сервер на loopback.
Проверяет оба HTTP-адаптера с выполнением action bodies, ответы, изоляцию двух
ресторанов, подмену admin полей, токены, первый/повторный визит, CRM, ограничения,
ошибки уведомлений и откат частичной записи при принудительном сбое CRM.

Письмо подтверждения проверяется через локальный HttpMessageHandler без обращения
к Resend. Тесты не используют production-секреты и не отправляют реальные push.
Они не заменяют тест конкурентных транзакций на PostgreSQL.
