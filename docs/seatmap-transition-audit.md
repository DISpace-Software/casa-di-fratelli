# Переход к SeatMap: аудит и этапы

Дата проверки: 3 ноября 2026 года. Этап 1 — локальный аудит текущего рабочего дерева, включая ранее подготовленные, ещё не закоммиченные изменения. Этап 2 — локальное переименование API, результаты ниже. Ссылки на код обновлены на новый путь.

## Вывод

Общий API уже умеет выбирать отдельную базу ресторана. Для SeatMap не требуется переписывать проект или заводить отдельный backend для каждого ресторана. Но универсальность бизнес-правил пока неполная: разделение баз само по себе не отделяет правила столов, зон и оформления Casa.

Фактическая стратегия — **отдельная база на ресторан с одинаковой схемой**, а не отдельные наборы таблиц внутри одной базы. Общая база платформы предназначена для профилей гостей, избранного и указателей на брони. Бронь и меню остаются в базе конкретного ресторана.

Это проверка кода и локальных тестов. Состояние Render, Vercel, DNS, секретов и production-баз в этом этапе не проверялось и не менялось.

## Переименование API (этап 2)

Название движка: **SeatMap**, техническое имя API: **SeatMap.Api**.

Выполнено согласованное переименование:

- `backend/CasaDiFratelli.Api/` и `.csproj` → `backend/SeatMap.Api/SeatMap.Api.csproj`;
- namespaces/usings и связанные ссылки на типы API;
- `backend/backend.sln` и ProjectReference во всех трёх проектах проверок;
- `backend/Dockerfile:6` (publish) и `:16` (запускаемый DLL);
- команды сборки/миграций и актуальные инструкции в README/docs.

Также обновлён namespace в генераторе `backend/scripts/generate-menu-seed.mjs`, чтобы следующая генерация меню не возвращала старое имя API. Исторический обзор `review-2026-09-05.md` сохраняет пути на дату того обзора.

Миграции, snapshots и design-time factories должны продолжать находить оба DbContext после смены namespace. Существующие migration IDs, таблицы и история применённых миграций сохраняются. Переименование не должно генерировать SQL изменения схемы. Названия старых проектов проверок можно перенести отдельным косметическим шагом.

Название ресторана **Casa di Fratelli**, tenant ID `casa-di-fratelli`, его домен, branding, ключ подключения `DefaultConnection` и существующая база остаются идентичностью первого ресторана. Глобальная замена всех упоминаний Casa на SeatMap недопустима.

### Имя сервиса и публичный адрес

В коде frontend есть действующий fallback `https://casa-di-fratelli-api.onrender.com` (`frontend/src/config/api.js:2`). Переименование проекта и DLL не требует немедленной смены этого адреса.

Изменение имени/адреса сервиса в Render — отдельный шаг после проверки реальных настроек hosting. Сначала инвентаризировать команды сборки/запуска, frontend `VITE_API_BASE_URL`, внешних клиентов и health checks. Если потребуется новый адрес, сначала обеспечить его работу, затем переключить клиентов и проверить старые ссылки/подтверждения. Нельзя считать, что переименование сервиса автоматически сохранит прежний URL.

## Порядок дальнейших этапов и критерии завершения

1. **Аудит (текущий этап).** Зафиксировать зависимости и проверить исходное состояние сборки и тестов.
2. **SeatMap.Api (локально выполнено).** Переименовать проект, сборку и references. Критерий: сборка, publish, все три набора проверок успешны; оба DbContext/миграции обнаруживаются; переименование не меняет схему и HTTP-контракты. Запуск Docker-контейнера остаётся непроверенным, пока Docker daemon недоступен.
3. **Независимые карты и правила.** Убрать общие Casa fallback из путей, используемых вторым рестораном. Критерий: неизвестный/неактивный стол отклоняется; одинаковые номера в двух ресторанах имеют независимые вместимость и зоны; пустая карта Cofein не превращается в Casa; существующие сценарии Casa проходят.
4. **Cofein в тестовом окружении.** Отдельная тестовая БД, уникальные credentials, frontend/origin, branding, меню и черновая карта с временными номерами. `SeedDefaultMenu=false`, `IsListed=false`; эти флаги не заменяют изоляцию тестового окружения. Письма и push направлены в тестовые приёмники. Критерий: полный путь сайт → API → база → подтверждение, отдельная админка и отсутствие данных другого ресторана. До реального запуска подтвердить вместимость и карту.
5. **Надёжность бронирования и мобильный контракт.** Защита от конкурентных пересекающихся броней во всех путях записи, idempotency, outbox с повторами. Проверки на PostgreSQL, включая одновременные сайт/приложение/админку.
6. **Профиль и приложение SeatMap.** Проверенная identity, `/me`, заполнение контактов на сервере, связь гостя с бронью, «Мои брони». Затем каталог → меню/карта → дата/время/гости → бронь/отмена. Если стол пользователь не выбирает, сервер должен подбирать доступный стол по правилам ресторана; сейчас TableIds обязателен.

Этапы выполняются отдельно, с отчётом о проверках. Разбиение backend на дополнительные проекты Domain/Application/Infrastructure можно делать по мере выделения сценариев; оно не является условием самого переименования.

## Границы готовности

- `RequireKnownTenant=false` пока сохраняет выбор Casa для запросов без селектора. Перед строгим режимом нужно зарегистрировать всех клиентов и health checks.
- Изоляция баз не изолирует падения общего процесса API и не заменяет отдельные права БД, резервное копирование и проверку восстановления.
- Проверка конфликта перед SaveChanges пока не гарантирует отсутствие двойного бронирования при конкурентных запросах.
- Публичный v1 пока принимает контакты гостя. Это ещё не сценарий бронирования из авторизованного профиля.
- Локальные SQLite/HTTP-проверки не доказывают корректность конкурентных PostgreSQL-транзакций и production-развёртывания.
