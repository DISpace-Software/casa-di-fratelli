# SeatMap: подготовка платформы и мобильного приложения

Дата: 3 ноября 2026 года.

## Целевая архитектура

```text
Сайты ресторанов     Приложение SeatMap     Админки ресторанов
        └──────────────────┼──────────────────────┘
                    Общий ASP.NET Core API
                  /                       \
      Уровень платформы              Уровень ресторана
      PlatformDbContext                AppDbContext
              |                             |
      Общая база SeatMap         База выбранного ресторана
      профили, избранное,         брони, контакты на момент брони,
      указатели бронирований     меню, залы, столы, сотрудники, CRM
```

Это модульный монолит: общий процесс API с отдельными областями ответственности
и базами. Выделение микросервисов сейчас не требуется. Изоляция баз не означает
изоляцию сбоев процесса API или ресурсов общего PostgreSQL-сервера.

## Что реализовано в подготовительном этапе

- `Platform/` — отдельный модуль платформы без зависимости от `CurrentTenant`.
- `PlatformDbContext` и отдельная PostgreSQL-миграция: глобальные профили гостей,
  избранное и указатели бронирований. Схема подготовлена, пользовательских API
  для чтения/изменения этих данных пока нет.
- Обязательное отдельное подключение `ConnectionStrings__SeatMapPlatform`.
  При включённой платформенной базе запуск проверяет, что её host/port/database
  не совпадают с базами ресторанов. Проверка строк не распознаёт DNS-алиасы одного
  сервера: инфраструктура также должна обеспечивать разные базы и права доступа.
- Каталог ресторанов из действующей конфигурации, без обхода ресторанных баз.
  `IsListed=true` явно публикует активный ресторан. По умолчанию новый ресторан
  не опубликован; Casa опубликован в текущей конфигурации.
- Версионированные публичные маршруты чтения для будущих клиентов SeatMap.
- Общий сервис создания и email-подтверждения брони для сайта и публичного v1 API.
  Подробнее: [общий сценарий бронирования](shared-booking.md).
- Явный выбор ресторана через маршрут и проверка конфликта с Origin/заголовком/host.
  Неизвестный ресторан в маршруте никогда не заменяется рестораном по умолчанию.
- Каталог работает без выбранного ресторана даже при `RequireKnownTenant=true`.
  Обход restaurant routing разрешён только endpoint-метаданными
  `PlatformEndpointAttribute`, а не произвольным префиксом URL.
- CORS обрабатывает preflight до tenant middleware. Общие web origins SeatMap
  задаются отдельно от доменов конкретных ресторанов.
- Миграции можно запускать отдельно от HTTP-процесса. Новая база платформы
  автоматически при обычном старте API не мигрируется.
- Новым ресторанам больше не выдаётся карта Casa, если собственной карты нет.
  Reset карты Casa доступен только Casa.

Изменения не включают готовое мобильное приложение, регистрацию гостей,
авторизацию глобального профиля или синхронизацию бронирований.

## Контракт API первого этапа

| Метод и маршрут | Назначение |
| --- | --- |
| `GET /api/v1/restaurants` | `{ restaurants: [...] }`, только активные опубликованные рестораны |
| `GET /api/v1/restaurants/{restaurantId}` | Публичная запись каталога или 404 |
| `GET /api/v1/restaurants/{restaurantId}/branding` | Действующий публичный branding ресторана |
| `GET /api/v1/restaurants/{restaurantId}/menu` | Действующее меню ресторана |
| `GET /api/v1/restaurants/{restaurantId}/layout` | Действующая схема столов ресторана |
| `GET /api/v1/restaurants/{restaurantId}/zones` | Закрытые сезонные зоны (`closedAreas`) |
| `POST /api/v1/restaurants/{restaurantId}/reservations` | Создать публичную бронь через общий сервис |
| `GET /api/v1/restaurants/{restaurantId}/reservations/confirm?token=…` | Подтвердить бронь по email |

Запись каталога содержит только `id`, `slug`, `name`, `websiteUrl`; подключения,
секреты администратора и внутренние настройки не выдаются. Каталог пока не
является поиском по городу/геопозиции и не содержит обогащённых карточек ресторанов.
Публичные названия каталога берутся из tenant-конфигурации, а подробный branding —
из ресторанной базы; до переноса каталога в управляемую базу поддерживайте их
согласованность при переименовании.

Маршруты чтения используют те же action-методы, что действующие сайты, без
дублирования бизнес-логики. Старые маршруты сохранены. Создание/подтверждение в v1
используют тот же сервис, что сайт; административные методы в v1 не добавлены.

`IsListed` управляет обнаружением в каталоге, а не секретностью сайта: прямые
публичные маршруты активного ресторана остаются доступны. `IsActive=false`
отключает routing ресторана полностью.

Пример для приложения:

```http
GET /api/v1/restaurants/casa-di-fratelli/layout
```

Native-приложение не обязано отправлять Origin или `X-Tenant-Id`: достаточно
явного ID в маршруте. ID ресторана выбирает контекст данных, но никогда не
подтверждает права сотрудника или владение бронью.

## Общая база

| Таблица | Ответственность |
| --- | --- |
| `GuestProfiles` | UUID гостя, внешний identity issuer/subject, имя, контакты |
| `GuestFavorites` | Уникальная пара глобальный гость + ресторан |
| `GuestReservationReferences` | Ресторан + локальный ID брони, гость, дата/время, статус и версия источника |

Одинаковые локальные ID бронирований разных ресторанов не конфликтуют. Пара
issuer/subject уникальна; одинаковые email или имена не объединяют аккаунты.
Пароли и ресторанные admin sessions в общей базе не хранятся.

Указатели — будущая восстанавливаемая проекция, а не вторая система записи брони.
Удаление профиля каскадно удаляет его избранное и указатели только из платформы;
ресторанная бронь от этого не удаляется. Политику хранения и удаления ресторанных
контактных данных нужно реализовать отдельно.

Пока не реализованы связь ресторанной брони с глобальным гостем, обработчик
событий и API «Мои брони». Существующие брони нельзя привязывать к аккаунту лишь
по совпадению телефона/email без подтверждения владения.

## Включение базы платформы

Подготовительная схема по умолчанию выключена: существующему ресторану новая
база не требуется. Каталог и публичные маршруты работают независимо от неё.

1. Создать отдельную пустую PostgreSQL-базу и отдельные credentials.
2. В секретах backend установить:

```text
Platform__Enabled=true
ConnectionStrings__SeatMapPlatform=<подключение отдельной PostgreSQL>
```

Допускается строка Npgsql или URL `postgresql://…`, как у ресторанных подключений.
Не задавать эти секреты во frontend. При обычном запуске база не мигрируется.

3. В deployment job с теми же backend-секретами выполнить:

```sh
dotnet run --project backend/SeatMap.Api --no-launch-profile -- --MigratePlatform=true
```

Команда проверяет конфигурацию подключений, применяет только платформенную
миграцию и завершает процесс до запуска HTTP и фоновых workers. Она не применяет
миграции ресторанов и не создаёт их владельцев. Не запускать две migration job
параллельно. В production можно запускать собранный DLL с тем же аргументом.

Фабрика `PlatformDbContextFactory` использует заведомо локальное design-only
подключение для генерации миграций/SQL. Для применения использовать команду выше,
а не `dotnet ef database update` без явно заданного подключения.

Инструмент EF Core закреплён в `.config/dotnet-tools.json`:

```sh
dotnet tool restore
dotnet ef migrations script --idempotent --context PlatformDbContext --project backend/SeatMap.Api
```

После добавления второго DbContext всегда указывайте `--context` в EF-командах.
Для текущей ресторанной схемы это `--context AppDbContext`.

## Отдельное применение миграций ресторанов

Совместимость сохранена: `Tenancy:MigrateOnStartup=true` по умолчанию.
Для перехода на отдельную deployment job:

1. Проверить резервные копии и прогнать job в тестовом окружении.
2. Перед запуском новой версии API выполнить:

```sh
dotnet run --project backend/SeatMap.Api --no-launch-profile -- --MigrateRestaurants=true
```

3. После успешного выполнения установить у HTTP-сервиса
   `Tenancy__MigrateOnStartup=false` и запускать его обычным способом.

Команда включает миграции, compatibility bootstrap, создание первого владельца
и настроенный menu seed для каждого активного ресторана. Ошибка прерывает job;
предыдущие базы могли уже обновиться. Схемы должны оставаться совместимыми с
предыдущей версией API на время развёртывания. До внедрения orchestration нельзя
считать миграцию всех ресторанов одной транзакцией.

## Общий web frontend SeatMap

Для будущего web-клиента платформы добавить точные origins:

```text
Platform__FrontendOrigins__0=https://app.<ваш-домен>
```

Не записывать общий домен SeatMap в `FrontendOrigins` одного ресторана: он должен
уметь выбирать разные рестораны. CORS не заменяет авторизацию; native-клиенты
и сторонние HTTP-клиенты не ограничиваются браузерным CORS.

## Следующие обязательные этапы до запуска приложения

1. **Общая identity и профиль.** Выбрать OIDC-провайдера и способ подтверждения
   контакта. Реализовать проверку issuer/audience/signature/lifetime токенов,
   `/api/v1/me`, безопасное редактирование профиля, удаление аккаунта и ограничения
   запросов. UUID гостя выводить из проверенной identity на сервере. Не принимать
   `SeatMapUserId` из тела запроса за доказательство личности.
2. **Бронирование из профиля и конкуренция.** Создание и подтверждение уже вынесены
   из `ReservationsController` в общий сервис. Добавить серверное заполнение
   имени/контакта из профиля, snapshot контактов, глобальную связь гостя с бронью,
   idempotency и атомарное предотвращение пересекающихся бронирований. Доказать
   конкурентными тестами на PostgreSQL, включая сайт + приложение + админку.
3. **Outbox и «Мои брони».** Записывать событие вместе с изменением брони в её
   ресторанной транзакции. Доставлять с повторами, дедупликацией и проверкой версии
   в общую проекцию. Поддержать создание, перенос, отмену, удаление, восстановление,
   сверку и повторную сборку проекции. Приложение должно учитывать задержку проекции.
4. **Универсальная карта.** Выделить явные сущности залов/зон/столов и правила
   объединения. Сейчас остаются Casa-specific IDs, capacity fallback, retired
   tables и фиксированные зоны в `ReservationsController`, `ReservationBookingService`, `TableCapacityService`,
   `SeasonalZoneService` и frontend. Исправление выдачи дефолтной карты не решает
   эти ограничения. Новые схемы посадки нужно проверять до публикации ресторана.
5. **Управляемый каталог.** Перенести публичные карточки, адреса, координаты,
   фотографии и параметры подключения ресторана в управляемый реестр; секреты
   хранить отдельно. Реализовать provisioning, публикацию и синхронизацию branding.
   Сейчас `Tenancy:Tenants` остаётся единственным источником routing-конфигурации.
6. **Стабильный мобильный контракт.** Описать OpenAPI, ошибки, пагинацию каталога,
   timezone и money/currency, availability, статусы брони и срок поддержки v1.
   Нынешние read aliases сохраняют существующие DTO и являются первым этапом.
7. **Эксплуатация и релиз.** Проверить восстановление каждой базы, метрики по
   ресторану, лимиты пула подключений, нагрузку, мониторинг workers, хранение PII
   и smoke tests нового ресторана и Casa. После регистрации всех вызывающих
   систем включить `RequireKnownTenant=true`.
8. **Мобильный MVP.** Каталог → карточка с меню/картой → дата/время/гости →
   подтверждение данными профиля → мои брони/отмена → push. Выбор конкретного
   стола или только зоны должен настраиваться рестораном.

## Проверки подготовительного этапа

```sh
dotnet build backend/backend.sln
dotnet run --project backend/CasaDiFratelli.TenancyChecks
dotnet run --project backend/CasaDiFratelli.ReservationChecks
dotnet run --project backend/SeatMap.PlatformChecks
```

PlatformChecks проверяет настоящую HTTP-маршрутизацию, boundary middleware и
SQLite-ограничения схемы; ресторанные action bodies в HTTP-пробах не выполняются.
PostgreSQL-миграция проверяется генерацией SQL, без подключения к production.
Это не проверка готовности мобильного бронирования к запуску.

ReservationChecks дополнительно выполняет настоящие HTTP booking actions обоих
адаптеров с двумя SQLite-базами. Границы этих проверок описаны в
[документе общего сервиса](shared-booking.md).
