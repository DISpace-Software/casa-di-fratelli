# Архитектура карт ресторанов

Для Cofein карта сайта, рабочая карта администратора и редактор используют один сохранённый план ресторана. Залы и столы задаются данными API. Cofein сохраняет архитектуру исходного помещения и четыре подробных вида; новые залы получают собственную область карты без изменения исходных столов. Реализация подготовлена локально 11 ноября 2026 года.

## Границы DDD

Предлагаемая структура — модульный монолит с общей платформой для ресторанов. Разделение предметной модели и отображения позволяет проверять правила независимо от интерфейса. Такой принцип соответствует описанию доменного, прикладного и инфраструктурного слоёв в [руководстве Microsoft по DDD](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/ddd-oriented-microservice).

| Модуль | Ответственность | Источник истины |
| --- | --- | --- |
| План ресторана | Залы, стабильные ID столов, номинальная вместимость, координаты, активность, версия карты | Агрегат `FloorPlan` в базе конкретного ресторана |
| Бронирования | Резервации, доступность, блокировки, сезонные закрытия, допустимые объединения и правила для гостя/персонала | Домен и API |
| Оформление карты | Архитектурная подложка, мебель, цвета, виды камеры, жесты и адаптация к экрану | Общий frontend renderer и визуальные шаблоны ресторанов |
| Прикладной слой | Авторизация, загрузка данных, вызов правил, транзакция сохранения, аудит и ответы HTTP | Сервисы приложения |
| Инфраструктура | PostgreSQL, изоляция ресторанов, хранение конфигурации, уведомления | Существующие адаптеры |

Правила Casa, например допустимые объединения для персонала, остаются в серверной конфигурации. Frontend может повторять проверку для удобства, но API проверяет её повторно. Цвет мебели или тип SVG-подложки не определяет число мест и возможность бронирования.

Зал и вид карты — разные понятия. В Cofein два зала бронирования (`interior`, `exterior`) и четыре подробных вида одного помещения. Переход к подробному виду не создаёт новый зал и не меняет границы сезонного закрытия.

Внешняя часть у улицы уже входит в `exterior`: вид `exterior-lower` содержит T08–T14 и T25–T26 (9 столов, 40 начальных мест). По исходной фотографии `20260907_162344.jpg` это нижний участок внешнего зала рядом с надписью «Улица». В интерфейсе он называется «Към улицата», верхний участок — «Към градината»; те же ориентиры используются в админке. Эти названия обозначают сторону помещения. Мебель снаружи за контуром здания на схеме не показана; отдельная садовая посадка не внесена как бронируемая зона без её номеров, расположения и вместимости.

## Публичный сценарий Cofein

В интерфейсе от 13 ноября посещение и выбор стола составляют одно рабочее пространство, по образцу Casa. На компьютере карта находится рядом с параметрами посещения. На телефоне сначала видны параметры, затем карта; кнопка «Промени» возвращает к тем же полям. Контакты заполняются после выбора стола в отдельной компактной форме. Возврат сохраняет заполненные контакты.

`CofeinVisitControls` — единственное место выбора даты, времени, гостей и зала. До четырёх залов отображаются кнопками, большее количество — нативным списком. Закрытые залы недоступны для выбора. Смена зала снимает выбранный стол; смена части карты сохраняет зал и стол. Список свободных столов использует тот же выбранный зал и не содержит второго переключателя залов.

`getCofeinBookingViews` строит только визуальные вырезки выбранного зала: `zoneId`, `tableIds` и границы кадра по активной мебели с небольшим запасом для ближайших стен. Доступность не меняет границы кадра. Координаты исходного плана, связи бронирований и вместимость остаются прежними. Миниатюры `CofeinMapPreview` и интерактивный `CofeinMapExplorer` используют одну геометрию, подложку и мебель. Публичный `scopeZoneId` ограничивает камеру и видимые столы выбранной частью; административный редактор без этого параметра сохраняет полный план.

Это разделение не требует новых бизнес-зон или изменений API: сервер отвечает за доступность и правила, frontend — за части карты, кадрирование и расположение формы. Новые залы получают вырезку по своим столам. Самостоятельное редактирование произвольных стен и этажей остаётся отдельным развитием визуальной модели ниже.

## Что реализовано

- Объединены ветка пространственной карты Cofein и актуальные исправления бронирований Casa, корзины, сезонной вместимости и локального голосового прототипа.
- `getCofeinMapGeometry` вычисляет общую сцену, виды и размещение столов. Публичное бронирование, редактор и рабочая карта используют её вместе с `CofeinFloorPlanDecor` и `CofeinTableVisual`.
- Добавление третьего и следующих залов сохраняет исходный план Cofein. Дополнительные залы получают отдельные области и кнопки перехода; отключённые залы исключаются из интерактивной геометрии. Неизвестные номера столов используют обычную мебель.
- Геометрия общей админки сохраняет расположение исходных зон Casa при получении дополнительных залов из API. Рестораны без собственного шаблона используют автоматически построенную сетку залов.
- Редактор позволяет добавить зал, изменить его название и активность, добавить столы, изменить вместимость и размещение. ID нового зала генерируется один раз и сохраняется при переименовании.
- Изменения залов и столов сохраняются одним `PUT /api/floor-plan` с исходной `revision`. Общие правила и комбинации сохраняются вместе с картой. Старая версия API Casa использует прежний адаптер `/api/table-layouts`.
- Черновик редактора отделён от сохранённой рабочей карты. Фоновое обновление не заменяет черновик и не подменяет его версию. Конфликт или неизвестный исход записи требуют загрузить актуальное состояние перед повторным сохранением.
- При добавлении нескольких столов редактор подбирает свободные позиции, учитывая минимальное расстояние, проверяемое API.

Формат API и схема базы для этого шага не менялись. Основная папка с незакоммиченными изменениями не использовалась для редактирования исходников; работа находится в отдельном постоянном worktree.

Публичная страница Casa пока использует старый клиент с тремя предопределёнными зонами. Поэтому новый раздел управления залами включён в общей админке для остальных ресторанов, включая Cofein; Casa сохраняет существующий редактор столов. Перед включением добавления залов Casa требуется перевести её публичную страницу на полный `floor-plan` и проверить прежние публичные правила. API и общая модель уже поддерживают этот переход.

## Контракт и ограничения

Существующий документ `schemaVersion: 1` содержит `zones`, `tables`, `combinations`, `publicMaxGuests`, `publicMaxTables`, `staffCombinationMode` и `revision`. ID зала используется в `table.area`; ID стола связывает план с историей бронирований. Переименование зала не меняет эти связи.

API принимает динамические списки, сохраняя защитные пределы: 50 залов, 500 столов и 2000 заданных комбинаций на ресторан. Вместимость одного стола — 1–500. Координаты лежат в диапазоне 5–95, расстояние между активными столами одного зала — не менее 6 единиц. Поэтому число столов в одном зале также ограничено доступным размещением. Для более крупных объектов нужно согласованно расширить контракт и проверить производительность API, редактора и отрисовки.

Сохранение защищено серверной проверкой роли, версии, существующих и будущих бронирований, блокировок и истории ID. Удалять стол с историей нельзя; отключение также не должно нарушать предстоящие бронирования. Сезонное закрытие остаётся отдельной операцией.

Существующее различие сохранено: Casa разрешает персоналу объединять столы одного зала, Cofein использует заданные комбинации. Публичные бронирования остаются ограничены вместимостью и публичными правилами. Найденный при аудите отдельный долг: лимит 40 гостей задан интерфейсом администратора, но не одинаково проверяется всеми серверными командами; этот шаг не меняет его семантику.

## Дальнейшее развитие модели

Сейчас `FloorPlanService` совмещает проверки и работу с EF. Для дальнейшего DDD-рефакторинга следует выделять чистые правила по одной группе с сохранением проверок совместимости: `VenueLayout` для структуры ресторана, `BookingPolicy` для правил выбора и `Reservation` для жизненного цикла брони. Прикладные команды загружают агрегаты и сохраняют результат через инфраструктуру; HTTP-контроллеры не определяют правила. Разделение классов не требует разносить приложение по сетевым сервисам.

Для редактируемых этажей, стен и индивидуальной мебели следующий совместимый шаг — отдельное версионированное описание визуальной сцены: ссылки на ID залов/столов, числовые границы, поворот, тип мебели, переводы названий и виды камеры. Хранить его нужно через API, чтобы все устройства получали одинаковое оформление. Рисование SVG, текстуры и поведение камеры останутся во frontend. Произвольный исполняемый HTML/SVG в конфигурацию не нужен.

Такое расширение требует сначала добавить и проверить серверный контракт и миграцию старых шаблонов, затем подключить редактор. В текущей реализации архитектура исходного Cofein остаётся визуальным шаблоном, дополнительные залы — прямоугольными областями; редактора произвольных стен и этажей пока нет.

## Проверка

Проверки охватывают проекцию и обратное преобразование координат, новые и отключённые залы, сохранение исходного Cofein и Casa, 50 залов и 500 столов, последовательное добавление столов, целостность черновика, полное сохранение карты и конфликты версий. Браузерная проверка использует отдельную локальную PostgreSQL-базу; производственные данные не изменяются.

Команды и результаты конкретного запуска находятся в `restaurant-map-verification.md`.
